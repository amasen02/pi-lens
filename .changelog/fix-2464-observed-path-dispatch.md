- **Give an observed (unclassified-tool) mutation its pipeline lint/diagnostics dispatch, without re-recording turn-state/change-log (#2464)** — `clients/runtime-tool-result.ts`'s early return for a provisionally-learned tool that is still armed (#2449 review round 4, S4) recorded three bridge-uncovered steps (the #2402 applied-edit records, `recordMutationToolReceipt`, the `cachedExports` refresh) and then returned, skipping the pipeline's own `runPipeline` dispatch entirely — the file was never linted/analysed that turn. It could not simply be re-enabled at that seam: the pipeline body it would have called is also what writes the duplicate `turn-state.json` range and change-log receipt the early return exists to suppress (the mutation bridge already recorded both). The pipeline dispatch (the `runPipeline` call, its crash handling, and its read-guard commit-status logging) is now factored into its own helper, `dispatchPipelineAnalysis`, called from two places: the classified chain (unchanged behavior — same arguments, same order, byte-identical) and the observed early return (new — analysis only, no second recording).

  Red before the fix, verbatim from `tests/clients/observed-mutation-integration.test.ts`'s new `#2464` case: `expect(vi.mocked(runPipeline)).toHaveBeenCalledTimes(1)` failed with `expected "spy" to be called 1 times, but got 0 times` on the pre-fix return. Mutation check: forcing the classified chain to also run for the same call (i.e. not gating dispatch behind the early return) turns the same assertion red the other way, `expected "spy" to be called 1 times, but got 2 times` — the test is non-vacuous in both directions. The existing `#2449 review round 3` (one receipt per physical edit) and `round 4` (S4, applied-edit records / receipt / cachedExports refresh) cases in the same file stay green, unmodified.
