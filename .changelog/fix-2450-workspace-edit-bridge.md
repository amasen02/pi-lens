- **LSP-applied edits (rename, `workspace/executeCommand`) now always bookkeep through the existing LSP mutation seam, and name the specific operation (refs #2450)** — `applyWorkspaceEdit`'s bookkeeping (`clients/lsp-mutation.ts` `bookkeepLspMutation`, from #1066) depends on its caller threading a `runtime`/`cacheManager` reference through `LspMutationContext`. One caller structurally cannot: `workspace/applyEdit`'s server-initiated-edit handler (`clients/lsp/client.ts`) builds its own fallback context with neither when `executeCommand` is invoked without a `mutationContext` (a real production shape — `clients/lsp/tsserver-sync.ts` calls it that way) — so a server-solicited write reached disk with zero bookkeeping: no read-guard stamp, no turn-state entry, no change-log receipt. `bookkeepLspMutation` now falls back to the mutation bridge (`clients/mutation-bridge.ts`, #2423) — mounted once at extension activation with live getters onto the SAME runtime/cache-manager singletons — for exactly that case, so the write is always recorded through one seam or the other, never silently dropped. Separately, every LSP-applied edit's change-log receipt now names the operation that produced it (`lsp-rename` / `lsp-execute-command`) instead of a generic `lsp-edit` tag that made a rename indistinguishable from an executeCommand-solicited edit.
