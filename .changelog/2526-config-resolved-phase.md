- **Config resolution now proves it happened (closes #2526)** — one `config_resolved` latency phase per session and served project root records the redacted `documents[]` (`{tier, file, legacy}`), `countsByTier`, `recordCount`, `deniedServers`, `resolveMs` and the session identity, with a matching `config resolved …` line in `sessionstart.log`. Written where the resolution already exists — `loadLSPConfig`, the one funnel every production resolution goes through — so nothing is resolved twice and the session-start hook path gains no await. The payload comes from `summarizeConfigResolution`, the same projection `pilens_effective_config` embeds, so the on-demand answer and the session record cannot drift. `handleSessionStart` publishes a `session_start config-resolution session=<id> expected=<bool>` line on both the quick and the full path, and `npm run logs:smells` gains a `config-resolution` smell that JOINS the two by session id: a session counts as unresolved only when its own start said a resolution was expected (LSP enabled, not a subagent, not a warm-attached quick start) and no record bearing its id exists. A legacy config document that produced zero migration records is the smell's second shape.
