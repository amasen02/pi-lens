- **Config resolution now proves it happened (closes #2526)** — one `config_resolved` latency phase per session and served project root records the redacted `documents[]` (`{tier, file, legacy}`), `countsByTier`, `recordCount`, `deniedServers`, `resolveMs` and the session identity, with a matching `config resolved …` line in `sessionstart.log`. Written where the resolution already exists — `loadLSPConfig`, the one funnel every production resolution goes through — so nothing is resolved twice and the session-start hook path gains no await. The payload comes from `summarizeConfigResolution`, the same projection `pilens_effective_config` embeds, so the on-demand answer and the session record cannot drift. `loadLSPConfig` also publishes a `session_start config_resolution_pending session=<id>` mark, as the first thing it does, so the mark fires exactly when a resolution is genuinely attempted rather than predicted from a handler's own flags ahead of time — a session that never reaches `loadLSPConfig` (e.g. a second quick- or minimal-mode session in the same process) publishes no mark and is correctly excluded, not counted against. `npm run logs:smells` gains a `config-resolution` smell that JOINS the two marks by session id: a session counts as unresolved only when it has a pending mark and no record bearing its id exists. A legacy config document that produced zero migration records is the smell's second shape.
